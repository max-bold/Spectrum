# Кэширование окон логарифмического сглаживания

## Задача для версии 0.4

Подумать над кэшированием окон, используемых `log_smooth()` и
`grid_smooth()`. Сейчас `_grid_smooth_real()` при каждом вызове заново вызывает
`log_window()` для каждой точки выходной сетки, хотя параметры окон обычно не
меняются между последовательными блоками анализатора.

## Причина

Для типичной конфигурации высокого разрешения использовался следующий benchmark:

- сетка центров: `np.geomspace(20, 20e3, 1024)`;
- длительность записи: `20 s`;
- частота дискретизации: `192 kHz`;
- размер FFT: `3_840_000`;
- шаг FFT: `df = fs / N = 0.05 Hz`;
- `log_window_old(width=0.33)`;
- `log_window(width=0.1)`.

Для Gaussian количество коэффициентов получилось близким:

| Реализация | Коэффициентов на 1024 окна | Время на 1024 окна |
|---|---:|---:|
| `log_window_old()` | 13 612 415 | 204.89 ms |
| `log_window()` | 13 019 059 | 201.91 ms |

Новая формула сама по себе не медленнее старой: при сравнимом количестве
коэффициентов время практически одинаковое. Однако при 10 000 генераций окон в
секунду только их построение требует около `1.97 CPU-секунды` на одну секунду
реального времени. После генерации `grid_smooth()` ещё выполняет взвешенное
усреднение тех же коэффициентов.

Сценарий воспроизведения: [`sandbox/benchmark_log_window.py`](../sandbox/benchmark_log_window.py).

## Что кэшировать

Кэшировать следует не результат сглаживания, а неизменяемый план окон. Для
каждого центра он может содержать:

- `data_start` и `data_end`;
- готовые веса с поправкой логарифмической меры `1/f`;
- при необходимости заранее вычисленную сумму весов;
- параметры, по которым был построен план.

Минимальный вариант структуры:

```python
@dataclass(frozen=True)
class SmoothingPlan:
    slices: tuple[tuple[int, int], ...]
    weights: tuple[np.ndarray, ...]
```

Более сложный вариант — разреженная матрица окон, умножаемая на входной спектр.
Перед выбором реализации нужно сравнить скорость и расход памяти обоих подходов.

## Ключ кэша

План должен перестраиваться при изменении любого параметра, влияющего на окна:

- длины и начальной частоты входной FFT-сетки;
- шага частот `frequency_step`;
- значений выходной сетки `grid`;
- типа `SmoothingWindow`;
- `width`;
- уровня обрезки окна, если он станет настраиваемым.

Нельзя использовать только идентификатор массива. `log_smooth()` создаёт новую
логарифмическую сетку при каждом вызове, хотя её значения могут оставаться
одинаковыми. Ключ должен строиться из параметров либо содержимого сетки.

## Ограничение памяти

Один Gaussian-план из benchmark содержит около 13 миллионов значений. В
`float64` это примерно `104 MB` без учёта служебных объектов. Поэтому
неограниченный `lru_cache` использовать нельзя.

Возможные ограничения:

- хранить только последний план для каждого анализатора;
- использовать LRU на 1–2 конфигурации;
- задать общий лимит кэша в байтах;
- отдельно проверить допустимость хранения весов в `float32`;
- не дублировать план для вещественной и мнимой частей комплексного спектра.

Последний пункт особенно важен: текущий `grid_smooth()` вызывает
`_grid_smooth_real()` отдельно для real и imaginary частей и дважды строит одни
и те же окна. Следует проверить возможность применять один план сразу к
комплексному массиву.

## Предлагаемый порядок реализации

1. Выделить построение окон в `build_smoothing_plan(frequency, grid, window, width)`.
2. Сделать применение плана отдельной операцией без вызовов `log_window()`.
3. Передавать или хранить план в долгоживущем объекте анализатора.
4. Для удобства оставить `log_smooth()` и `grid_smooth()` совместимыми с текущим API.
5. Добавить ограниченный внутренний кэш как запасной путь для прямых вызовов функций.
6. Устранить двойное построение окон для комплексных данных.

## Критерии готовности

- повторный вызов с теми же параметрами не вызывает `log_window()`;
- изменение любого элемента ключа корректно перестраивает план;
- результат численно совпадает с текущим `grid_smooth()`;
- поддерживаются одномерные, многоканальные и комплексные значения;
- кэш потокобезопасен либо принадлежит одному worker/анализатору;
- максимальный объём памяти явно ограничен;
- benchmark показывает выигрыш на повторных вызовах;
- тесты покрывают cache hit, cache miss, инвалидирование и комплексные данные.
